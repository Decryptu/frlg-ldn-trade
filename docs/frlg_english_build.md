# Building the other cartridge pair, and measuring ours with it

This project reads a **French** FireRed and a **French** LeafGreen, a kilobyte at a time, through the
Mystery Gift link. The decompilation is the source those cartridges were built from, but it is not
the cartridges: it has no addresses in it, only the order things are declared in.

`pret/pokefirered` builds a ROM. It builds **both** cartridges, and it builds them at **REVISION 10**,
which is the revision the Switch release runs:

    make firered_switch     -> pokefirered_switch.gba    baa452d0b24629dd7782cfc07a8984085dde1311
    make leafgreen_switch   -> pokeleafgreen_switch.gba  62b9fc77549dbc67032eb6cbd0ea6ad3b825690f

Both come out byte-identical to the sha1 the decomp pins, on a machine with binutils and `pret/agbcc`
and nothing else. `scratchpad/build_decomp.sh` does the whole thing in about two minutes, and **the
sha1 is the only reason any of what follows is worth reading** - a build that does not match is a
build of something else.

## It is not our cartridge, and that is the point

The build is the ENGLISH release. At the same address the French console and the English build agree
on **3.7%** of their bytes: French text is a different length, and everything after a string moves.
Nothing here can be read as "the address in the build is the address on the console".

What it is instead is a **second cartridge pair**, from the same source, in the same link order, with
every symbol, section and object known. Two pairs, and the question is how far apart they are.

## The offset: French address -> English address

A French address and an English address hold the same function whenever their bytes agree, and the
difference between them - call it the OFFSET - is piecewise constant. It steps only where an object
changes size between the languages, which in a code region is rare: measured runs here are tens of
kilobytes long and one of them is 1.3 MB.

Two independent readings give it, and they agree everywhere both speak.

**The tables, free.** `gSpecials[i]`, `gScriptCmdTable[i]` and `gMysteryEventScriptCmdTable[i]` are
the same function on both builds, so entry *i* on the console and entry *i* in the English ROM are an
offset point. 675 of them, out of dumps this project already had, with no fingerprinting and no run.

**The dumps.** A 16-byte window that occurs **exactly once** in the English ROM places any French
bytes equal to it. A kilobyte of code carries a few hundred such windows, so one block votes hundreds
of times for one offset, and a step inside a block shows up as two runs rather than a wrong answer.

    ./.venv/bin/python tools/frlg/english_build.py --offsets

## The control, which is why any of this is allowed

The English build proposes a name for a French address: take the offset, add it, read the name off
the English ELF - which carries **static** functions, unlike the link map.

Run that against `worker_names`, every name this project measured off the console's own function
bodies, and it comes back **232 agree, 0 disagree**. Not one contradiction.

    ./.venv/bin/python tools/frlg/english_build.py --check

The one that looked like a disagreement was not: `GetBoxMonData2` is
`__attribute__((alias("GetBoxMonData3")))` [decomp:src/pokemon.c:3332], one function with two
symbols. The reader now keeps every name an address carries.

**A name from here is a DEDUCTION.** `rom_map.CALLABLE` still means "called on hardware and something
happened" and `worker_names` still means "the console's own body called it in the order the source
says". `pokeldn/frlg/rom/english_names.py` holds 7573 French function addresses named this way,
generated by `scripts/gen_english_names.py`, with the offset runs beside them so a later session can
extend or argue with the measurement rather than the conclusion.

The immediate payment: of the **177 call targets this project could not name, two are left**.
158 fall inside a measured offset run and are named outright. The rest fall BETWEEN two runs, and
those get a weaker reading of their own in `english_names.BRACKETED`: named with one of the two
offsets either side, accepted only when it lands exactly on a function start and only one of the two
does. An offset wrong by two bytes lands mid-instruction, which is what stands in for the missing
measurement, and `rom_functions` marks them `[english?]` against `[english]` for the rest.

**The corroboration worth keeping.** Three of those call targets are reached from a dozen bodies
each and had survived every reading this project could do. The English build reads them as
`__divsi3`, `__modsi3` and `__umodsi3` - and session 42, naming workers by zipping a body's calls
against the decomp's, had already said the residue would be exactly that: agbcc emitting a helper
for a division nobody wrote. Neither reading knew anything about the other.

## The LeafGreen delta map

`docs/frlg_leafgreen.md` has the map itself. What the build adds is that **the English pair's own
delta map is computable exactly**, by comparing the two English ROMs to each other - and it comes out
as the same six values the French cartridges measured, in the same order:

    +0x0   -0x2c   -0x28   -0x24   -0x20   -0x1c4

Each step happens **inside a version-divergent object, not at its edge**, which is why the link map's
symbols do not bracket it: the code inside `title_screen.o`, `mystery_event_script.o`,
`mystery_gift.o` and `pokemon.o` that differs between FireRed and LeafGreen carries no symbol common
to both builds. Byte comparison brackets each step to between 79 and 1606 bytes.

    ./.venv/bin/python tools/frlg/english_build.py --boundaries

Carried across by the offset map, that is a PREDICTION of where the French boundary is - and every
one of the five landed inside the bracket this project had already measured, which is five
independent agreements between two methods that share nothing.

## The measurement that needs no build at all

The prediction is not the proof, and the proof turned out to be cheaper than the prediction.

**Dump both cartridges at the SAME address.** If the delta there is *d*, the LeafGreen block holds
what the FireRed block holds shifted by *d*, and any *|d|* under a kilobyte leaves hundreds of bytes
of overlap. Cross-correlating the two blocks reads *d* straight off, with no English build, no
symbol, no needle and no guess about where the twin is - which is exactly what a bisection cannot do
when the delta is the unknown.

That is what closed it. bs127/lg193 dumped 27 scattered kilobytes on each cartridge and every block
answered; two boundaries fell INSIDE a block, and inside a block the step is readable to the byte by
asking, window by window, which delta still matches.

The same trick is what makes a scattered pair cheap to aim: **a LeafGreen block does not have to be
aimed at a FireRed block's twin.** Send the same address list to both consoles.

## Traps

- **A `.gcc2_compiled.` symbol sits at the first symbol of its file** and will shadow the function
  name if the reader keeps only the first symbol at an address. Skip names beginning `.` or `$`.
- **Padding matches at every delta.** A window has to say something before its match means anything;
  16 distinct byte values is the threshold used here, and without it the 0xFF filler between objects
  reads as agreement with whatever was asked.
- **The offset is not the delta.** The offset is French -> English on ONE cartridge. The delta is
  FireRed -> LeafGreen on the console. They are related by
  `french delta = offsetFR - offsetLG + english delta`, and that identity is what lets two scattered
  joins measure a delta the two English builds already know how to describe.
- The build is a ROM and is never committed. `english_names.py` and the offset runs in it are the
  durable part; regenerate them with `scripts/gen_english_names.py` after any new dump.
